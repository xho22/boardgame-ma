# 测试验收文档

本文档定义每个开发阶段完成时必须进行的验证。实际命令以项目落地后的 `package.json` 为准；如果某阶段尚未配置对应命令，需要在阶段交付中说明原因。

## 1. 验收原则

- 每个阶段都必须有可检查的输出物。
- 每个阶段都必须运行至少一种自动验证，除非项目尚未初始化。
- 规则逻辑优先用单元测试验证，UI 流程优先用浏览器手动检查或 Playwright 验证。
- 如果测试失败，阶段不能标记完成。
- 如果某项验证暂时无法运行，必须在交付说明中记录原因和后续补救点。

## 2. 标准验证命令

常用命令：

```text
npm run test
npm run build
npm run dev
npm run lint
```

阶段早期可能还没有全部命令。最低要求：

- 项目初始化后必须能运行 `npm run build`。
- 规则引擎出现后必须能运行 `npm run test`。
- UI 可用后必须能通过手动浏览器检查。
- Playwright 引入后必须覆盖桌面、平板、手机三个视口。

## 3. 阶段验收清单

### 阶段 0：项目初始化

输出物：

- 前端项目可启动。
- 首页非空白。
- 基础目录结构存在。

验证：

- `npm install`
- `npm run build`
- `npm run dev`
- 浏览器打开本地地址确认页面可见。

### 阶段 1：规则数据模型

输出物：

- `GameState`
- `Player`
- `Athlete`
- `RaceState`
- `GameCommand`
- seed 随机数

验证：

- `npm run test`
- 2 人、4 人、6 人初始化测试通过。
- 每局状态可 `JSON.stringify`。

### 阶段 2：基础角色池

输出物：

- 标准版 36 个角色数据。
- 第一批简单能力标记可实现。

验证：

- 角色 id 不重复。
- 每个角色有标准版名称、显示名、能力摘要、实现 key。
- 角色池足够支持 2-6 人每人 4 名角色。

### 阶段 3：本地状态管理与页面流程

输出物：

- 新游戏设置。
- 队伍展示。
- 本地存档与继续游戏。

验证：

- `npm run build`
- 创建 2 人局。
- 刷新后可继续。
- 2-3 人局可以选择每名玩家每场 1 或 2 名 racer；4-6 人局只能选择 1 名。
- Teams 页面可点击 `Randomize Teams` 重新随机所有玩家手牌。
- Teams 页面角色卡显示小图，能力说明通过跟随鼠标的浮层显示，不应撑开列表高度。

### 阶段 4：秘密派遣流程

输出物：

- 玩家逐个选择角色。
- 锁定遮挡页。
- 统一揭示页。

验证：

- 玩家 1 锁定后，玩家 2 看不到玩家 1 选择。
- 全部锁定后揭示正确。
- 已使用角色不可再次选择。
- 2 racer 模式下，每名玩家必须选满 2 名 racer 才能锁定；Race Reveal 页面每名玩家显示 2 名 racer。

### 阶段 5：基础比赛引擎

输出物：

- 掷骰。
- 移动。
- 冲线。
- 前两名结算。
- 4 场后最终排名。

验证：

- `npm run test`
- 2 人比赛可结束。
- 2 人每人 2 名 racer 时，场上应有 4 枚棋子，回合顺序以 racer 为单位。
- 第一名、第二名积分正确。
- 4 场后进入终局。

### 阶段 6：比赛 UI

输出物：

- 赛道。
- 棋子。
- 骰子按钮。
- 比赛日志。
- 赛后和终局页面。
- 骰子滚动动画。
- 棋子移动动画。

验证：

- `npm run build`
- 手动完成 2 人 4 场。
- 桌面和手机尺寸无明显重叠。
- 点击掷骰后，数字应在约 2 秒内快速变化，再展示真实结果。
- 棋子从起点移动到目标格时，应逐格移动，而不是瞬间跳到终点。
- 比赛日志应记录掷骰、移动、冲线和得分。

### 阶段 7：第一批能力

输出物：

- Alchemist
- Coach
- Gunk
- Hare
- Legs
- Magician
- Rocket Scientist

验证：

- 每个能力至少 1 个正常测试。
- 日志能说明能力触发。
- 日志能说明能力触发条件和造成的结果。
- Legs 必须能选择直接移动 5 格，也必须能选择放弃能力并正常掷骰。
- Rocket Scientist 必须能选择不使用加倍能力。
- 不引入死循环。

### 阶段 8：复杂移动与第二批能力

输出物：

- trip
- passing
- sharing a space
- onOtherPower 响应
- 第二批角色能力

验证：

- 自动模拟 100 局不卡死。
- 多人同格、passing、trip 恢复测试通过。
- 复杂移动、后退、跟随和 warp 均有动画或高亮反馈。
- 连锁触发的日志顺序与规则结算顺序一致。

### 阶段 9：完整 36 角色能力

输出物：

- warp
- 预测
- 复制
- 淘汰
- 回合顺序改写
- 完整 36 名角色能力

验证：

- 自动模拟 1000 局不卡死。
- 每个角色至少 1 个能力测试。
- Mastermind 在开赛前必须能选择具体预测 racer；预测命中时 Mastermind 自动成为第 2 名并结束比赛。
- 鸡蛋在阵容揭示后随机展示 3 名未参赛候选，玩家选择其中 1 名能力；双胞胎在已有历史冠军时，从此前第一名角色列表中选择要复制的能力。
- 每名玩家派出 2 名 racer 时，行动顺序按玩家交错：玩家 A 的第 1 名、玩家 B 的第 1 名、玩家 A 的第 2 名、玩家 B 的第 2 名。
- Gunk 必须让其他 racer 的 main move -1，日志说明原移动值和最终移动值；该触发应能带动 Scoocher move 1。
- 完整 2 人局可手动跑通。

### 阶段 10：体验打磨

输出物：

- 动画。
- 快速模式。
- 大字模式。
- 规则页。
- 响应式优化。

验证：

- 390 x 844 手机视口。
- 768 x 1024 平板视口。
- 1440 x 900 桌面视口。
- 主要按钮可点击，文字不溢出。
- 同一玩家派出 2 名 racer 时，棋盘棋子应显示不同角色头像，而不是相同玩家首字母。
- trip 中的 racer 头像应倒置；恢复后头像恢复正向。
- trip 中的 racer 轮到行动时，当前行动区应提示“绊倒恢复中”，并自动进入下一回合，不要求玩家掷骰。
- 比赛日志使用中文显示。
- 鸡蛋和双胞胎的赛前选择未完成时，开始比赛按钮不可用。
- 最新日志位于最上方，日志序号保留真实追加顺序。
- 日志超过可视区域后可以滚动查看历史。
- before main move 可选能力有明确交互：Legs、Flip Flop、Cheerleader、Hypnotist、Third Wheel。
- Genius 必须在掷骰前提供主动猜点流程；猜中才获得额外回合。
- Suckerfish 必须在同格目标移动后弹出是否跟随的确认；确认完成后比赛再继续。
- after-roll 选择类能力若尚未实现暂停确认，需要在计划文档中保留明确缺口。

### 阶段 11：在线房间技术验证

输出物：

- 固定房间。
- WebSocket 或等价同步机制。
- 两个窗口可加入同一房间。

验证：

- 两个浏览器窗口状态同步。
- 一个窗口占座后另一个窗口可见。
- 房主离开或刷新后状态处理符合设计。

### 阶段 12：在线完整游玩

输出物：

- 服务端权威状态。
- 客户端发送 `GameCommand`。
- 私密选择按玩家过滤。
- 两端完整比赛流程。

验证：

- 两个浏览器窗口完成 2 人 4 场。
- 非当前玩家不能掷骰。
- 玩家不能选择别人的角色。
- 刷新后能回到自己座位。

## 4. 测试计划

## 4.1 单元测试

重点测试：

- 角色分配数量正确
- 每个角色只能选择一次
- 第一名和第二名产生后比赛结束
- 积分发放正确
- 平局规则正确
- 刷新后恢复状态

## 4.2 能力测试

每个能力至少写 2 个测试：

- 正常触发
- 边界情况

边界情况包括：

- 起点
- 终点
- 多人同格
- 同时触发
- 已冲线角色
- 跳过回合
- 后退到起点前

## 4.3 自动模拟

实现一个无 UI 模拟器。

目标：

- 随机跑 1000 局
- 确认不会死循环
- 统计角色胜率
- 统计平均触发次数
- 找出明显过强或过弱角色

## 4.4 浏览器测试

使用 Playwright 检查：

- 1440 x 900 桌面
- 768 x 1024 平板
- 390 x 844 手机

检查项目：

- 文字不溢出
- 按钮可点击
- 赛道不遮挡
- 棋子可见
- 动画后状态正确
